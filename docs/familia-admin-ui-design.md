# Familia Admin UI: Design Study and Developer Datasheets

Scope: a web admin/management surface for Familia v2.10.1 models (Horreum), their
relations and relationships, standalone DataType records, and the underlying
Redis/Valkey database, built on Otto v2.1.1 and Rack 3. Researched against the
admin-framework canon (Django, Ash, Phoenix, Rails, Laravel) and the Redis/Valkey
GUI landscape.

Versions verified at source: Familia `2.10.1` (git HEAD == `v2.10.1` tag), Otto
`2.1.1`, Rack `3.1+` required by Otto, Ruby `3.2+`.

---

## 0. Bottom line up front

1. **Build a model-aware admin, not another key browser.** Every existing Redis
   GUI (RedisInsight, Redis Commander, phpRedisAdmin, ARDM, DbGate) works at the
   key/data-structure level. None understands that `customer:abc:object` is a
   `Customer` Horreum with typed fields, encrypted columns, indexes, and a
   relationship graph. That model awareness is the entire reason to build this,
   and Familia already exposes it at runtime.

2. **Drive it from runtime introspection, not codegen.** Familia models are
   declarative and self-register in `Familia.members` at boot. The admin needs no
   per-model scaffolding; one generic introspection-driven API serves every model.
   This is the Ash "declare once, derive the rest" pattern, and Familia is already
   shaped for it.

3. **Ship one gem with two deployment modes.** Mounted into the host app
   (full, model-aware, the primary product) and standalone (raw Redis/Valkey
   explorer only, or fed an exported model descriptor). A truly generic
   "any Redis server" tool cannot be model-aware without the host app's classes,
   so do not pretend phpMyAdmin's fully-decoupled posture is achievable for the
   model layer. It is achievable only for the raw layer.

4. **Expose an API plus an MCP server, do not generate a frontend.** Otto turns a
   plain-text routes file into both a JSON HTTP API and JSON-RPC 2.0 MCP tools.
   Emit a machine-readable model descriptor (`GET /admin/api/_meta`) and an
   OpenAPI document, and let frontend teams (or AI agents) build against it.

5. **The differentiator is integrity and migrations, not CRUD.** Familia already
   ships a full audit/repair framework (`health_check`, `repair_all!`, phantom and
   stale-index detection, cross-reference drift) and a migration runner with
   schema-drift detection. Redis has no server-side constraints, so surfacing
   Familia's application-level integrity is uniquely valuable. This is "fsck for
   your object graph," and no Redis GUI or SQL admin offers it.

## 1. What "autogenerated admin" means (the canon)

The frameworks that defined this category all do the same three things: introspect
a declarative model, derive a UI/API from it, and provide escape hatches for
customization. The recurring feature set:

| Capability | Django admin | Ash (AshAdmin) | Rails (ActiveAdmin / Avo) | Laravel Filament | Phoenix (Kaffy / Backpex) |
|---|---|---|---|---|---|
| Auto model registration / introspection | `admin.site.register` + model meta | derived from resource DSL | resource DSL / zero-config | resource classes | derived from Ecto schema |
| List view: columns, filter, search, sort, paginate | `list_display`, `list_filter`, `search_fields` | derived + actions | yes | tables + filters | yes |
| Detail/form: field widgets, validation, readonly | `fieldsets`, `readonly_fields` | from attributes + validations | yes | forms | yes |
| Related-record editing | inlines | relationships | has_many panels | relation managers | assoc fields |
| Bulk + custom actions | `actions` | resource actions | batch actions | table/page actions | custom actions |
| Permissions / policies | per-model/object perms | Ash policies | Pundit/CanCan | policies | per-resource |
| Change history / audit log | `LogEntry` | (extension) | paper_trail/Avo | activity log | (manual) |
| Derive an API too | DRF separate | AshJsonApi + AshGraphql | separate | separate | separate |
| Runtime telemetry | no | no | no | no | **LiveDashboard** (separate) |

Two members of this set matter most for Familia:

- **Ash** is the closest philosophical match. A single declarative resource powers
  migrations, validations, an admin UI, a JSON:API, and a GraphQL API. Familia
  models are similarly declarative and already carry the metadata (fields, types,
  indexes, relationships, JSON Schema) needed to derive the same artifacts.
- **Phoenix LiveDashboard** is the model for the *operational* half: live runtime
  metrics, process/ETS/Ecto stats. It is not a CRUD admin. Familia's
  `Instrumentation` hooks and `ThreadSafety::Monitor` make an analogous live
  Redis/Familia dashboard possible.

The lesson: a great admin is the *projection of a declarative model into a
generic UI*, plus an operational dashboard, plus an API for everything else.
Familia can supply all three projections from one source of truth.

## 2. The reframing that decides the architecture

phpMyAdmin works because a SQL database carries its own schema. `INFORMATION_SCHEMA`
tells the tool every table, column, type, index, and foreign key with zero help
from the application. Point it at any MySQL server and it is instantly useful.

Redis/Valkey has **no schema**. The keyspace is a flat namespace of opaque values.
The "schema" for a Familia application lives entirely in the Ruby model classes:
which prefixes map to which models, which hash fields are typed columns, which are
encrypted, which sorted sets back which relationships, which hashkeys are unique
indexes. A tool that connects only to the server sees `customer:abc:object` as an
anonymous hash. It cannot know it is a `Customer`, that `secret_key` is a
`ConcealedString`, or that `customer:abc:domains` is a sorted set participating in
a relationship.

Consequence, stated plainly: **a model-aware Familia admin must run with the host
application's model classes loaded, or be fed an exported descriptor of them.**
There is no `INFORMATION_SCHEMA` to substitute. This single fact drives the
"mountable engine" recommendation in section 5 and is the honest boundary against
the phpMyAdmin analogy.

The good news: once the classes are loaded, Familia's runtime introspection is a
richer metaobject protocol than `INFORMATION_SCHEMA`. It knows encryption status,
relationship cardinality, index staleness, TTL policy, and serialization rules,
which a SQL catalog never exposes.

## 3. Feature catalog for a Familia admin (answers Q1)

Mapped to the exact Familia API that powers each feature. All API references are
verified against the 2.10.1 source tree.

### 3.1 Model browser

- Enumerate every model from `Familia.members` (auto-populated by the `inherited`
  hook on `Familia::Horreum`). Resolve by name via `Familia.member_by_config_name`
  / `Familia.resolve_class`.
- Per model, render the schema card from class introspection: `fields`,
  `field_types` (each a `FieldType` with `name`, `category`, `persistent?`,
  `transient?`), `identifier_field`, `prefix`, `suffix`, `logical_database`,
  `related_fields` and `class_related_fields` (the attached DataTypes),
  `relations?`, `field_groups`.
- Distinguish field categories visually: plain field, `encrypted_field`
  (ConcealedString), `transient_field` (RedactedString, never persisted), and
  related DataTypes. Use `persistent_fields` vs `transient_fields`.

### 3.2 Record CRUD

- **List**: default to `scan_count` (production-safe SCAN) for totals and the
  `instances` sorted set timeline for time-ordered, paginated listing. Avoid
  `all` and `keys_count` in the default path (both block; `all` is `KEYS` + load).
  Load pages with `load_multi` / `multiget`.
- **Read**: `find_by_identifier(id, check_exists:)` or `find_by_dbkey(key)`.
  Render through `safe_dump` when the model declares safe-dump fields, so the API
  never leaks secrets by default.
- **Create**: `build(...) { |o| ... }` (folds the save and all collection writes
  into one MULTI/EXEC, create-only) or `create!`.
- **Update**: scalar edits via setters then `save`, or `name!(value)` fast-write;
  wrap multi-field or field+index edits in `atomic_write` so the record and its
  indexes commit atomically.
- **Delete**: `destroy!(id)`.
- Every mutating action should run inside `transaction`/`atomic_write` and be
  written to an admin audit log (see 6.7).

### 3.3 Relationship navigation

- Read the object graph from the introspection layer: per class
  `indexing_relationships` and `participation_relationships`; project-wide
  `Familia.index_descriptors`, `Familia.unique_indexes`, `Familia.multi_indexes`,
  `Familia.participation_descriptors` (all live as of 2.10.1).
- Each `IndexDescriptor` is navigable without knowing storage layout:
  `coordinate` (human-readable location), `each_record(value:, scope:)` to walk
  the records behind an index bucket, `rebuild!`, `stale_format?`. Use these to
  render "follow this relationship" links and bucket browsers.
- Follow related DataTypes with `each_record` (loads linked Horreum records via
  `load_multi`, with the `record_class:` loading hint added in 2.10.1).
- Render generated finders (`find_by_<index_name>`) as first-class query forms.

### 3.4 DataType inspectors (owned and standalone)

- One editor per registered DataType, using native operations: ListKey,
  UnsortedSet, SortedSet, HashKey, StringKey, JsonStringKey, Counter, Lock
  (full registry in Appendix B).
- Lean on the Enumerable iteration added in 2.9.0/2.9.1: `SortedSet#each(since:,
  until:)` for time-range browsing, `HashKey#each(matching:)` and
  `UnsortedSet#each(matching:)` for glob-filtered scans, `ListKey#each(batch_size:)`
  for paginated lists. These map directly to server-side ZRANGEBYSCORE / HSCAN /
  SSCAN / LRANGE, so the admin paginates without loading whole collections.
- **Standalone DataType records** (not owned by a Horreum), e.g. a
  `Familia::StringKey.new('session:abc')` or a free-standing leaderboard sorted
  set. The admin should let you address these by raw key and edit them with the
  same typed editors, bridging the model layer and the raw layer.

### 3.5 Querying

Be explicit about cost. Redis is not SQL; there is no general `WHERE`.

- **Indexed lookups** (O(1)/O(log n)): `unique_index` finders and `multi_index`
  bucket browsing via `IndexDescriptor#each_record(value:)`.
- **Range queries**: sorted-set score/time ranges via `SortedSet#each(since:,
  until:)`.
- **Pattern scans**: `scan_keys(filter, batch_size:)` and the `matching:` forms,
  always SCAN-based.
- **Ad-hoc field filtering** (no index): full scan plus load plus in-Ruby filter.
  Surface this in the UI as an expensive operation with an explicit row budget,
  and prompt the user to add an index. Do not present it as cheap.

### 3.6 Integrity (the headline feature)

Wrap Familia's audit/repair framework directly:

- `health_check(...) => AuditReport` (`healthy?`, `to_h`, `to_s`). Component
  audits: `audit_instances` (phantoms vs missing, timeline-vs-scan counts),
  `audit_unique_indexes` (stale/missing), `audit_multi_indexes` (stale_members,
  orphaned_keys), `audit_participations`, `audit_related_fields`,
  `audit_cross_references`.
- One-click repair with dry-run first: `repair_all!(verify:)`, `repair_instances!`,
  `rebuild_instances`, `repair_indexes!`, `repair_multi_indexes!`,
  `repair_participations!`, `repair_related_fields!`.
- Boot-time and on-demand stale-index guard: `Familia.stale_indexes` and
  `Familia.assert_indexes_current!(on_stale: :warn|:raise)`.
- Progress callbacks are built into the audit/repair methods (they `yield`
  `{phase:, current:, total:}`), so stream progress to the browser over a Rack 3
  streaming body.

### 3.7 Migrations

Wrap `Familia::Migration`:

- `Runner#status`, `#pending`, `#validate`, `#run(dry_run:, limit:)`, `#run_one`,
  `#rollback`, `#topological_sort` (dependency ordering).
- `Registry#schema_drift` and `#schema_changed?(model_class)` compare the live
  model against the stored `schema_digest`. This powers a "your model drifted,
  here is the diff, here is a suggested migration" cockpit.
- `Registry` backups: `backup_field`, `restore_backup`, `clear_backup`, with
  `backup_ttl` configurable.
- Built-in Lua `Script` registry for safe field operations: `rename_field`,
  `copy_field`, `delete_field`, `rename_key_preserve_ttl`,
  `backup_and_modify_field`. Expose these as guided, atomic admin operations.

### 3.8 Raw Redis/Valkey terminal and explorer

- A guarded command console (allowlist by default, dangerous commands gated by
  permission, see Appendix K), key explorer with TYPE/TTL/MEMORY USAGE, and
  server `INFO` panels.
- Live command feed from `Familia::Instrumentation` (`on_command`, `on_pipeline`,
  `on_error`) streamed via a Rack 3 streaming body (SSE), plus slowlog and the
  `DatabaseCommandCounter` middleware totals.
- `ThreadSafety::Monitor#report` / `export_metrics` for contention and health.

### 3.9 Security and special-field handling

- Encrypted fields render as `[CONCEALED]`; `reveal` is a separate, permission-
  gated, audit-logged action. Show key version and envelope version; never log
  plaintext.
- Transient fields are never sent to the client (they are `[REDACTED]` and not
  persisted anyway).
- TTL/expiration cockpit: `ttl`, `expire_in`, `default_expiration`, cascading
  expiration; optionally surface server field-level TTL (HEXPIRE family) for
  hashes (see section 6.6).

## 4. Can Familia generate the app and API from the host project? (answers Q2)

Yes, and the right mechanism is a generic, introspection-driven engine plus a
machine-readable descriptor, not per-model code generation.

**Why not codegen.** Generating controllers/routes per model duplicates metadata
that already exists at runtime and immediately drifts when a model changes. Ash,
Pocketbase, Supabase, and Directus all derive their admin and API at runtime from
the live schema for exactly this reason. Familia is already there: models register
themselves and answer every introspection question listed in Appendix A.

**What the engine does.** A single set of generic endpoints handles all models:
`/_meta` (the full descriptor), `/:model` (list), `/:model/:id` (CRUD),
`/:model/:id/:datatype` (collection ops), `/:model/_index/:index` (indexed
queries), `/_integrity/*` (audit/repair), `/_migrations/*`, `/_raw/*` (explorer).
Each resolves the model via `Familia.resolve_class` and reflects with Appendix A.

**The admin management API plus docs (not a frontend).**

- Emit a **resource descriptor** at `GET /admin/api/_meta`: for every model, its
  fields with category and type, identifier, key pattern, indexes with
  cardinality and coordinate, participations, safe-dump field set, TTL policy, and
  (if present) the JSON Schema from `SchemaRegistry`. Appendix J is a worked
  example. Familia already pairs models with JSON Schema documents
  (`examples/schemas/customer.json`), so the descriptor can embed real validation
  contracts, not guesses.
- Generate an **OpenAPI 3.1** document from the same descriptor so any frontend,
  SDK generator, or API client consumes it without bespoke knowledge.
- Because Otto routes can also be declared `MCP` (resources) and `TOOL`
  (actions), the same definitions expose a JSON-RPC 2.0 MCP server at `/_mcp`.
  The admin API is then drivable by AI agents for audits, repairs, and migrations
  with zero extra work. This is genuinely differentiated (section 6.8).

The frontend stays out of scope by design. You ship the API, the descriptor, the
OpenAPI doc, and the MCP surface. Frontend teams build whatever they want against
a stable, self-describing contract.

## 5. Standalone tool vs mountable engine (answers Q3)

Committed recommendation: **one gem, mountable-first, with a raw standalone mode.**

The decision follows directly from section 2. Model awareness requires the host
app's classes. Therefore:

- **Primary mode (mounted).** The gem mounts into the consuming Rack/Otto app
  (`run Familia::Admin.new` under a path, or as Rack middleware). It runs in the
  app's process with all models loaded, so `Familia.members` and full
  introspection are available. This is where 90 percent of the value lives:
  model browsing, typed CRUD, relationship navigation, integrity, migrations,
  encryption-aware display.

- **Secondary mode (standalone).** A separate process pointed at a Redis/Valkey
  URI gives the raw explorer, terminal, key browser, server stats, and live
  command feed. No model awareness. This is the "works against any server" tool,
  and it competes (modestly) with RedisInsight/Redis Commander, so keep it lean
  and do not over-invest.

- **Bridge: the exported descriptor.** The mounted engine can export the resource
  descriptor (section 4) to a file or endpoint. A standalone deployment, or a
  decoupled frontend, can load that descriptor plus a live connection and recover
  most model awareness without importing the Ruby classes. This is how you get as
  close to phpMyAdmin's decoupling as the schemaless substrate allows.

Why not a fully separate "phpMyAdmin for Redis" project: that product already
exists several times over at the raw layer and is commoditized. The defensible,
novel product is the model-aware layer, and that layer is structurally tied to
Familia and the host app. Build the thing only you can build.

Naming: `familia-admin` (engine + API) is the clean split, optionally with a
`familia-explorer` for the raw standalone if you want independent release cadence.

## 6. Novel opportunities Familia uniquely enables (answers Q5)

What this admin can do that generic Redis GUIs and even SQL admins do not.

### 6.1 Model-aware browsing over a schemaless store
The core novelty. Typed columns, encrypted fields, relationships, and indexes
rendered over what other tools see as anonymous hashes and sets.

### 6.2 Integrity console: fsck for the object graph
Redis enforces no referential integrity. Familia's audit framework already detects
phantoms (instances-timeline entries with no key), missing entries, stale index
formats, orphaned index buckets, stale participation members, and cross-reference
drift, with one-click repair and dry-run. No Redis GUI has this; SQL admins lean
on the database's own constraints, which Redis lacks. This is the strongest reason
the tool should exist.

### 6.3 Relationship graph visualization
`index_descriptors` + `participation_descriptors` describe the whole object graph:
which sets/sorted sets back which relationships, cardinality (unique vs multi),
scope (class-level vs instance-scoped), and score semantics for sorted sets.
Render it as a navigable graph. SQL admins draw FK diagrams; here you draw the
actual Redis structures behind each edge.

### 6.4 Encryption-aware operations
Show `ConcealedString` fields as concealed, gate `reveal` behind permission and
an audit entry, display key version and envelope version, and offer key-rotation
tooling (Familia stores `envelope_version` and `aad_fields` per value and supports
versioned keys with `current_key_version`). A "fields encrypted under retired key
v1, re-encrypt to v2" workflow is something no general DB admin offers.

### 6.5 Schema-drift and migration cockpit
`Registry#schema_drift` plus `schema_digest` turn "I changed a model" into a
visible diff and a suggested, reversible, backed-up migration using the built-in
Lua field operations. This is closer to Rails/Ash migration tooling than to any
Redis GUI.

### 6.6 TTL intelligence, including field-level TTL
Familia's `expiration` feature is whole-key. Recent Redis/Valkey added per-hash-
field TTL (HEXPIRE, HGETEX, HSETEX, HTTL family). The admin can surface and manage
field-level expiry that the model layer does not yet model, and flag fields whose
server TTL diverges from the model's policy. (Version note: hash-field expiration
is Redis 7.4+, and on the Valkey track its exact GA version should be confirmed
against your target; sources place it at Valkey 8.1/9.0. Treat the exact floor as
a config check, not a hardcoded assumption.)

### 6.7 Atomic, audited admin mutations
Admin edits that touch a record and its indexes commit in a single MULTI/EXEC via
`atomic_write`/`build`, so the admin never leaves half-written index state. The
2.10.0 unsaved-parent guard means the admin enforces correct write ordering by
construction. Most admin tools issue a sequence of writes and hope.

### 6.8 MCP-native administration
Because Otto exposes `TOOL`/`MCP` routes as JSON-RPC 2.0 at `/_mcp`, the admin API
is simultaneously an agent interface. An AI operator can run a health check,
propose a repair, or dry-run a migration through the same contract a human UI uses.
A database admin tool that is natively agent-drivable is, as of now, novel.

### 6.9 Safe-dump as the serialization boundary
`safe_dump` gives every model an explicit allowlist of client-safe fields. Make it
the default response serializer so the admin cannot accidentally leak secrets to
the frontend. Security-by-default at the data boundary is rare in admin tooling.

## 7. Honest constraints (where not to overpromise)

- **No general query language.** Only indexed lookups, range scans, and pattern
  scans are cheap. Everything else is scan-and-load. Design the UI around this;
  do not imply SQL-like filtering.
- **Listing has failure modes.** The `instances` sorted set can hold phantoms;
  `all`/`KEYS` block. Default to SCAN and the audit tools, and show counts as
  "timeline vs scan" so discrepancies are visible rather than hidden.
- **Multi-database and cluster.** Models can live in different `logical_database`
  values; `atomic_write` requires one logical DB and (on Cluster) one hash slot,
  raising `CrossDatabaseError` otherwise. Cross-model atomic operations are
  constrained; the admin must respect and surface this.
- **Model awareness needs the classes.** Reiterated from section 2: the rich
  features only work mounted or via an exported descriptor.
- **Reveal/raw-command power is dangerous.** Encryption reveal, FLUSHDB, KEYS,
  arbitrary commands, and destroy must be permission-tiered and audited
  (Appendix K).

## 8. Proposed architecture (one possible shape)

```
host app (Rack 3)
└── mount Familia::Admin at /admin
      ├── Otto router  (plain-text routes: auth=, response=json, csrf=, MCP/TOOL)
      │     ├── HTML shell (optional, minimal) for the bundled frontend
      │     ├── JSON admin API  (generic, introspection-driven)
      │     └── /_mcp  JSON-RPC 2.0 (resources + tools)
      ├── Introspection layer  → Familia.members + Appendix A reflection
      ├── Command layer (Otto Logic classes: one per admin action)
      │     initialize(context, params, locale); raise_concerns; process
      ├── Integrity service     → audit/repair framework
      ├── Migration service     → Familia::Migration::Runner/Registry/Script
      ├── Raw explorer service  → SCAN/TYPE/TTL/INFO + Instrumentation feed
      └── Security              → Otto auth strategies + RBAC + audit log
```

Why Otto specifically: the plain-text route file already encodes per-route auth
(`auth=role:admin`, `auth=api_key`), content type (`response=json`), CSRF policy
(`csrf=exempt`), and MCP/TOOL exposure. Authentication strategies (api_key,
session, role, permission) and the `StrategyResult` RBAC object are built in.
The Logic-class handler gives each admin action a clean
`(context, params, locale)` signature with a `raise_concerns`/`process`
lifecycle, which is the natural unit for an audited admin command. Otto's
auto-registered HTTP error classes plus `register_error_handler` give consistent
JSON error responses.

Why Rack 3 matters here: streaming bodies (`body.call(stream)`) let you stream
audit/repair progress, the live command feed, and large SCAN exports as
server-sent events without hijack gymnastics, and bidirectional streaming enables
a live terminal.

| `list`, `listkey` | `ListKey` | list | ordered, dup-allowed; `each(batch_size:)` -> LRANGE pages |
| `set`, `unsorted_set` | `UnsortedSet` | set | unique; `each(matching:)` -> SSCAN MATCH |
| `sorted_set`, `zset` | `SortedSet` | zset | scored; `each(since:, until:)` -> ZRANGEBYSCORE; `update`/`merge!` bulk ZADD |
| `hash`, `hashkey` | `HashKey` | hash | field->value; `each(matching:)` -> HSCAN; `update`/`merge!` |
| `string`, `stringkey` | `StringKey` | string | scalar |
| `json_string`, `json_stringkey`, `jsonkey` | `JsonStringKey` | string | JSON-encoded scalar; render as JSON editor |
| `counter` | `Counter` (< StringKey) | string | atomic INCR/INCRBY |
| `lock` | `Lock` (< StringKey) | string | mutex semantics; show holder/TTL, allow force-release with care |

Shared: all DataTypes `include Enumerable` (2.9.0) so `each`, `each_slice`,
`lazy`, `map`, `find` work. `each_record(batch_size:, write_size:, **filters)`
loads Horreum records (not raw IDs) via `load_multi`, filtering ghost entries.
The `record_class:` option (2.10.1) is a loading hint for `each_record`.

## Appendix C. Field-category and security-display rules

| Category | Persisted | Client display default | Reveal path |
|---|---|---|---|
| plain `field` | yes | value (subject to safe_dump) | n/a |
| `encrypted_field` (ConcealedString) | yes (ciphertext) | `[CONCEALED]` | permission-gated, audited `reveal` |
| `transient_field` (RedactedString) | no | `[REDACTED]`, never sent | never |
| related DataType | yes (separate key) | link/inline editor | n/a |

Rule: serialize list/detail responses through `safe_dump` when the model declares
safe-dump fields (`safe_dump_field`, `safe_dump_fields`, `safe_dump_field_names`,
`safe_dump_field_map`). Never include transient fields. Never include encrypted
plaintext except on an explicit, audited reveal.

Encryption facts for the UI: providers are AES-256-GCM and XChaCha20-Poly1305
(plus a hardened variant). Keys are versioned (`encryption_keys: {v1:, v2:}`,
`current_key_version`). Each ciphertext stores `envelope_version` and `aad_fields`.
Surface key version per field and offer rotation to the current key.

## Appendix G. Key/identity and connection model

Key shape: `prefix:identifier:suffix` (suffix defaults to `object`). Build with
`Class.dbkey(identifier, suffix)`; the instances timeline is a per-class sorted
set scored by creation time (drives time-ordered listing and `count`).

Connection: `Familia.uri=`, `Familia.connection_provider=` (e.g. ConnectionPool),
`create_dbclient`, `dbclient`. Per-class `logical_database` selects the DB.
Middleware: `DatabaseLogger` (with `capture_enabled` toggle) and
`DatabaseCommandCounter`. Atomic primitives: `atomic_write(*instances,
watch_keys:, pre_check:)` (one MULTI/EXEC, optimistic lock with backoff),
`build`, `transaction`, `pipelined`. Cross-DB or cross-slot atomic writes raise
`CrossDatabaseError`.

## Appendix H. Otto v2 route DSL and capabilities

Routes file is plain text. Verbs: `GET POST PUT DELETE PATCH`, plus `MCP`
(read-only resource) and `TOOL` (action). Per-route parameters:

- `response=json|view|redirect|auto` (content type / negotiation)
- `csrf=exempt` (opt out of CSRF for APIs/webhooks)
- `auth=authenticated|role:NAME|permission:NAME|api_key`

Auth strategies: `api_key`, `session`, `role`, `permission`, `noauth`. The
`StrategyResult` (in `env['otto.strategy_result']`) answers `authenticated?`,
`has_role?`, `has_permission?`, `roles`, `permissions`, `user_id`, `user_context`,
`to_h`.

Handlers: `Controller.action` (class method), `Controller#action` (instance),
lambda, and Logic class (`initialize(context, params, locale)` then
`raise_concerns` and `process`).

MCP: `Otto::MCP::Server#enable!` mounts `POST /_mcp` (JSON-RPC 2.0). `Registry`:
`register_resource`, `register_tool`, `list_resources`, `list_tools`,
`read_resource`, `call_tool`. Bearer-token auth, rate limiting, schema validation
included.

Security middleware: CSRF, input validation, rate limiting, IP privacy/masking,
security headers, trusted proxies. Errors: `Otto::NotFoundError` (404),
`BadRequestError` (400), `UnauthorizedError` (401), `ForbiddenError` (403),
`PayloadTooLargeError` (413), auto-registered; customize with
`register_error_handler(klass, status:, log_level:)`. Lifecycle:
`on_route_matched(env, route_definition)`, `on_request_complete`,
`register_handler_wrapper`, `freeze_configuration!`. Requires Ruby 3.2+,
Rack 3.1+.

## Appendix I. Rack 3 facts that matter here

- Streaming body: return a body that responds to `call(stream)` and use
  `stream.write`/`stream.close` for SSE (progress feeds, live command stream,
  large exports) and bidirectional streaming (live terminal). Enumerable bodies
  (`each`) are for buffered responses; expose `to_ary` when bufferable.
- Headers: lowercase keys, mutable hash, `Array` for multiple values; `Rack::Headers`
  auto-lowercases. Status must be an `Integer >= 100`. Response array must be mutable.
- `rack.input` is not required rewindable (efficient large uploads/imports).
- `rack-session` and `rackup` are separate gems in Rack 3.

## Appendix K. Security checklist for the admin

- Tier permissions: read, write, reveal-secrets, run-migrations, raw-command,
  destructive (FLUSHDB/destroy). Map to Otto `auth=role:`/`permission:`.
- Default response serializer is `safe_dump`; transient fields never serialized;
  encrypted plaintext only via audited, permission-gated `reveal`.
- Raw command console: allowlist by default; block/deny-list KEYS, FLUSHALL,
  FLUSHDB, CONFIG, SHUTDOWN, DEBUG unless explicitly elevated; rate-limit.
- All mutations atomic (`atomic_write`/`transaction`) and written to an
  append-only admin audit log (who, when, action, target key, before/after digest).
- CSRF on by default for state-changing browser routes; `csrf=exempt` only for
  token-authenticated API/MCP routes.
- Honor `logical_database` and Cluster hash-slot limits; refuse cross-DB atomic
  operations rather than silently splitting them.
- MCP/TOOL endpoints behind bearer-token auth and rate limiting; destructive
  tools require the same elevated tiers as their HTTP equivalents.
